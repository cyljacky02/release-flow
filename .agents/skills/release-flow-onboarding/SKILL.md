# 專案接入

建立可審查、可重跑的接合層；部署邏輯使用指定版本的共用核心。

## 1. 定位與探索

先區分兩個根目錄：

- **ProjectRoot**：本次要接入／修改的專案；從使用者指定位置及該 repo 的指示確認。
- **ReleaseFlowRoot**：核心來源。此 skill 隨 release-flow repo 安裝時，是 skill 目錄往上三層；先核對 [README](../../../README.md) 與 `src/ReleaseFlow.psm1`。若 skill 被單獨搬移或來源不符，取得使用者指定的核心位置及版本再繼續，不把 ProjectRoot 當成核心來源。

記錄核心版本與內容摘要。讀 ProjectRoot 的指示、實際 build 入口、產物、目標設定及 GitLab includes；檔案／匯出 API 是命令與 schema 的來源，不從範例猜測。

**完成條件**：兩個根目錄、核心來源／版本／摘要、build 命令、產物位置及依賴皆有來源證據；未知項目具名列出。

## 2. 契約與能力閘門

根據需求讀取相關權威文件：領域用語見 [GLOSSARY](../../../GLOSSARY.md)；多目標、核准與復原取捨見 [設計共識](../../../docs/design/deployment-workflow-v1.md) 對應章節；現有支援與操作限制見 [操作指南](../../../docs/operations.md) 及核心實作。若使用其他核心來源，改用該來源的對應文件。設計共識描述目標，不是實作能力證明。

請使用者決定 repo 無法回答的部署需求。逐目標列出識別、建置變體、受管理／保護範圍、非秘密設定來源、服务與驗證、復原政策，以及 local／GitLab 執行環境。

建立「需求 → 核心 API／實作證據 → 支援／未支援／未知」表。未支援能力列為阻擋項，提出縮減範圍或另行開發的選項並等待決策；模擬 DEMO 與真實部署是兩種範圍。未知 runner 資訊可保留為明確停用的待配置範本，不得宣告遠端可執行。

**完成條件**：每個需求及目標有決策與能力判定；執行範圍內沒有未解決阻擋項。核心來源未確認前只做探索，不生成替代部署核心。

## 3. 產生／修改入口

先呈現變更計畫，再按所選分支執行：

- **新增接入**：使用已核對的核心範例建立專案入口，替換專案特有命令與設定。
- **修改既有接入**：盤點受影響腳本、jobs、includes、rules、needs 與 artifacts；提出最小差異，保留無關流程。新建範本不是覆蓋既有 pipeline 的理由。

本地與 GitLab 引用相同權威 build／package 命令及核心。從隔離目錄演練端到端流程；依建置變體共用 build，按目標組裝及投遞。正式投遞、遠端修改與憑證操作需另外明確授權。

產生操作文件時引用已確認的部署契約與核心操作指南，只補專案特有路徑、順序、核准參考及例外處理。

**完成條件**：提供檔案差異、local／GitLab 入口到共用命令的對照，以及逐目標套件清單；核對目標設定隔離、秘密排除、delivery 的對應 package 依賴及既有流程保留。待配置入口預設停用。

## 4. 驗證與交付

執行真實 build 前說明依賴與副作用並取得許可。依已選範圍及核心驗收案例，在全新本地隔離目錄驗證；修改既有流程亦驗證受影響的原有路徑。

記錄每項驗證的命令、退出狀態、證據位置及通過／失敗／未執行。修正失敗後重跑對應案例。需要 runner 或遠端 CI Lint 的驗證，僅在有環境與授權時執行；本地 YAML 解析不等於 GitLab 相容性驗證。

**完成條件**：交付檔案清單、核心來源／版本／摘要、已選契約、逐目標清單、命令對照與驗證紀錄。明列待配置、阻擋及未驗證項目；區分 local、GitLab、真實 Windows 行為，不以本地成功推論正式可用。若範圍被阻擋，交付診斷與所需決策，不標示接入完成。
